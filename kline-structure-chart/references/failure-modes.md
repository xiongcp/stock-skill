# 小模型执行本技能时最容易犯的错

本文件只用于理解错误类型。**不要在回答里引用本文件中的任何数字**，所有点位一律以本次脚本输出的 JSON 为准。

## 一、为什么不能用任何图像生成工具画图

扩散生图模型画K线和推演图时会出现以下事故：
1. **文字乱码**：英文 `Infographic` 被画成 `Infogcaph`，中文被画成「休投板流流量」「MAb60」之类的乱码。
2. **涨跌颜色画反**：把下跌阴线画成红色，而A股是红涨绿跌。
3. **双指数混轴**：把上证指数和创业板指画在同一根价格轴上，刻度顺序还会颠倒。
4. **伪造已发生K线**：把未来的K线画成实体红绿K线，让用户误以为已经收盘。

**正确做法**：始终运行主入口 `scripts/analyze_and_forecast.py`（同时产出 JSON、PNG 与 HTML）。PNG 由脚本画出真实的轨道、ABC 测算线与右侧三条推演折线，配色随市场（A股/港股红涨绿跌，美股绿涨红跌）。

## 二、写文字分析时的常见错误

回答的骨架以本次生成的 `*_report.md` 为准（见 `SKILL.md` 回复契约），需要补充细节时再查 `*_result.json`；`*_chart_data.json` 不是稳定接口，不要引用。

| 序号 | 常见错误 | 正确做法 |
| --- | --- | --- |
| 1 | 自己心算加减法或黄金分割点位 | 原样复制 `*_report.md` 的表格与点位，或取自 `*_result.json` 的 `structure.fib_levels`、`structure.key_levels`；回复中的价格必须在 `quotable_prices.prices` 内。 |
| 2 | 漏写形态轨道、ABC 测算位或三条推演路径 | 完整转述 `structure.channel`、`structure.abc_scenario`（或报告对应章节）与 `scenarios.paths` 的触发、目标、失效。 |
| 3 | 把不同指数的点位串在一起 | 上证只看上证的 JSON，创业板只看创业板的 JSON，每个指数单独成段。 |
| 4 | 把 ABC 的 A 浪低点当成窗口最低点 | A 浪端点只看 `structure.abc_scenario.a_start` / `a_end`，C 浪最远位置只看 `c_progress`，不要自行从K线里找高低点替换。 |
| 5 | 编造概率（如"上涨概率 60%"、"大概率突破"），或把 `verdict.rule_score`、状态分说成胜率 | 推演路径按「触发条件 → 目标价 → 失效条件」转述，不附加任何概率、胜率或频率数字；唯一例外是回测成交胜率，必须带样本量 n 与 95% 区间，并说明是已发生成交的统计。 |
| 6 | 把成交量写成"成交额 XX 万亿" | 只抄报告里的"为5日均量的 X 倍、20日均量的 Y 倍"（`indicators.momentum.rvol20` 等）。 |
| 7 | 收盘后还写"盘中未收盘"，或沿用早盘的旧低点 | 每次回答都重新运行脚本，数据说明只抄本次 `quality.notes` 与 `meta.as_of`。 |
| 8 | 按教科书改判形态（如"下降楔形，所以必然上涨"） | 形态和突破方向以 `structure.channel.status_text` 为准。比如脚本写的是"收盘跌破下轨（向下突破）"，就不能说成"看涨楔形"。 |
| 9 | 盘中刚越过某个价位，就写成"已经跌破/突破" | 触发条件里带「盘中已跌破，待收盘确认」的，回复里也必须保留"待收盘确认"。 |
| 10 | 只贴模板，没有回答用户的具体问题 | 先用 1~2 句话、只用 JSON 里的数字直接回答，再给完整报告。 |
| 11 | 用户要看最近 300 天，就把形态说成"300日楔形"，或把年线、长周期黄金分割当成明天的突破位 | 形态、浪型和三条推演永远只基于近 120 日；大级别背景只描述位置，不当作触发位或目标位。 |

## 三、消息面与资金面数据

两融余额、ETF 申赎、开户数、主力资金净流入/流出、海外 CPI 等数据，本脚本不计算。如果本轮对话没有用专门工具查到一手数据，在文字中一律注明「未复核」，不要从历史对话记忆里抄数字。

## 四、Flash / 轻量模型发出回复前 8 项必过自检表（Checklist）

在使用 Flash 模型生成最终回复前，逐条对照以下 8 项（也可直接运行 `scripts/lint_response.py` 自动检查）：

1. **否决是否置顶**：若 `verdict.risk_veto == true`，回复第一段是否已明确写出「风控否决」及原因，且未给出任何做多买入建议或买入股数（`plan.long.position_sizing.recommended_shares` 为 `null` 时转述 `reason`，不得自行用风险预算换算股数）？
2. **价格是否零改写**：回复中的所有价格是否与 `*_report.md` 完全一致（保留原本的 2 位或 3 位小数，未做四舍五入或心算加减）？
3. **规则分是否严守边界**：提到 `verdict.rule_score` 时是否明确称为「确定性规则加权分」，从未出现「规则分对应胜率/上涨概率/置信度」？
4. **是否没有任何概率数字**：除回测成交胜率（必须带样本量 n 与 95% 区间）外，回复里是否没有概率、胜率、频率或「大概率」「胜算」之类的措辞？
5. **正常波动范围是否注明无方向**：引用 `volatility_range` 时，是否说明「中枢 q50 = 最新收盘价，只描述波动幅度，不含方向预测」，并同时给出实测覆盖率与独立样本数？
6. **板块特性是否提醒到位**：若标的为 `688`（科创板）或 `300/301`（创业板）等 20% 涨跌幅高弹性品种，是否提醒了「严格在 `plan.long.entry_zone` 区间内挂单、避免短期乖离追高」？若激活「超跌反弹」且处于空头趋势，是否提醒了「待日线收阳站上触发位右侧确认」？
7. **是否通过 `scripts/lint_response.py`**：把拟发送的回复存成文件，用本次 `result.json` 运行校验，输出 `"status": "OK"` 后再发送？
8. **结尾免责声明是否保留**：文末是否包含「以上为规则化技术分析，仅供研究参考，不构成投资建议」？
